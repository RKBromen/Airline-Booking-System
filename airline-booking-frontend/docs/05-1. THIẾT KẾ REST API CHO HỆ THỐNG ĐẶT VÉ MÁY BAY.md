# THIẾT KẾ REST API CHO HỆ THỐNG ĐẶT VÉ MÁY BAY
## 1. Tổng quan thiết kế API
Hệ thống sẽ được chia thành 10 module chính.
Mục tiêu thiết kế:
- API tuân theo RESTful conventions.
- Phân chia rõ chức năng của `CUSTOMER`, `STAFF` và `ADMIN`.
- Các thao tác đặt vé, giữ ghế và thanh toán phải được kiểm soát bằng transaction.
Transaction (giao dịch cơ sở dữ liệu) là một nhóm các thao tác SQL được thực hiện như một đơn vị công việc duy nhất.
Mục đích của Transaction là đảm bảo rằng:
- COMMIT: Tất cả thao tác trong transaction được thực hiện thành công và các thay đổi được xác nhận.
- ROLLBACK: Nếu xảy ra lỗi, các thay đổi chưa được commit trong transaction sẽ bị hủy, dữ liệu quay về trạng thái trước transaction.

# MODULE 1. AUTHENTICATION & AUTHORIZATION
## 1.1. Mục đích
### 3.1. Mục đích
Module này xử lý đăng ký tài khoản, đăng nhập bằng email/password, đăng nhập qua Google/Facebook, xác thực JWT và phân quyền theo Role.

## 1.2. Danh sách API

| Method | Endpoint                                 | Chức năng                       | Role          |
| ------ | ---------------------------------------- | ------------------------------- | ------------- |
| POST   | `/api/v1/auth/register`                  | Đăng ký bằng email/password     | PUBLIC        |

| GET    | `/api/v1/auth/oauth2/google`             | Bắt đầu đăng nhập Google        | PUBLIC        |

### API đăng nhập Google/Facebook
#### API 1. Đăng nhập Google
`GET /api/v1/auth/oauth2/google`
Chức năng:
1. Người dùng chọn đăng nhập Google.
2. Backend chuyển hướng người dùng đến Google.
3. Người dùng xác thực và đồng ý chia sẻ thông tin cần thiết.
4. Google chuyển hướng về callback kèm Authorization Code.
5. Spring Security kiểm tra `state` và đổi Authorization Code lấy token từ Google.
6. Backend xác minh danh tính Google.
7. Tìm tài khoản theo `provider = GOOGLE` và `provider_user_id`.
8. Nếu đã liên kết, đăng nhập vào tài khoản tương ứng.
9. Nếu chưa liên kết, xử lý tạo tài khoản mới hoặc yêu cầu liên kết theo chính sách hệ thống.
10. Backend phát hành JWT của hệ thống.
Với Google, nên sử dụng OpenID Connect và định danh `sub` đã được xác minh.
#### API 2. Đăng nhập Facebook
`GET /api/v1/auth/oauth2/facebook`
Quy trình tương tự Google nhưng sử dụng OAuth2 và API của Facebook để lấy, xác minh danh tính người dùng.
Không giả định Facebook luôn cung cấp email. Nếu không có email hợp lệ, hệ thống cần yêu cầu người dùng bổ sung và xác minh email trước khi hoàn tất tạo tài khoản.
#### API 3. Response sau khi đăng nhập thành công
Sau khi xác thực Google/Facebook thành công, backend phát hành token của chính hệ thống:
```
{
  "accessToken": "jwt-access-token",
  "refreshToken": "refresh-token",
  "tokenType": "Bearer",
  "expiresIn": 3600
}
```
Đây là cấu trúc kết quả logic. Với ứng dụng web, không nên đưa Access Token hoặc Refresh Token trực tiếp vào URL callback. Có thể sử dụng một mã đăng nhập ngắn hạn, dùng một lần để frontend đổi lấy token, hoặc dùng cookie bảo mật phù hợp.
### API lấy tài khoản đã liên kết
`GET /api/v1/auth/providers`
Response `200 OK`:
```
{
  "providers": [
    {
      "provider": "GOOGLE",
      "linked": true
    },
    {
      "provider": "FACEBOOK",
      "linked": false
    }
  ],
  "hasPassword": false
}
```
API này giúp frontend xác định người dùng đã liên kết phương thức đăng nhập nào.
### Business Rules bổ sung
- Tài khoản tạo bằng Google/Facebook mặc định nhận role `CUSTOMER`.
- Tài khoản `BLOCKED` hoặc `DELETED` không được đăng nhập bằng bất kỳ phương thức nào.
- Không sử dụng Google Access Token hoặc Facebook Access Token thay cho JWT của hệ thống.
- Không tự động gán role `ADMIN` hoặc `STAFF` dựa trên thông tin từ Google/Facebook.
- Không cho phép hủy liên kết phương thức đăng nhập cuối cùng nếu tài khoản chưa có phương thức đăng nhập thay thế.
- Tạo `users`, `user_roles` và `user_auth_providers` trong cùng một Database Transaction.
- Xử lý đăng nhập đồng thời bằng UNIQUE constraint và transaction để tránh tạo tài khoản trùng.
- Xác minh `state`, sử dụng PKCE khi phù hợp và bảo vệ callback khỏi login CSRF.
## 1.3. Request và Response
### API 1. Đăng ký tài khoản
`POST /api/v1/auth/register`
Request:
```
{
  "email": "customer@gmail.com",
  "password": "Password@123",
  "fullName": "Nguyen Van A"
}
```
Response `201 Created`:
```
{
  "id": "user-uuid",
  "email": "customer@gmail.com",
  "fullName": "Nguyen Van A",
  "status": "ACTIVE",
  "roles": ["CUSTOMER"]
}
```
Business Rules:
- Email không được trùng.
- Password phải được hash bằng BCrypt.
- Người dùng đăng ký mới mặc định nhận role `CUSTOMER`.
- Không trả `password_hash` trong response.
- Tạo user và gán role trong cùng một transaction.
### API 2. Đăng nhập
`POST /api/v1/auth/login`
Request:
```
{
  "email": "customer@gmail.com",
  "password": "Password@123"
}
```
Response `200 OK`:
```
{
  "accessToken": "jwt-access-token",
  "refreshToken": "refresh-token",
  "tokenType": "Bearer",
  "expiresIn": 3600
}
```
Business Rules:
- Kiểm tra email và mật khẩu.
- Chỉ tài khoản `ACTIVE` được đăng nhập.
- JWT chứa `userId` và thông tin vai trò cần thiết.
- Refresh Token cần được lưu hoặc quản lý an toàn để hỗ trợ thu hồi.
### API 3. Lấy tài khoản hiện tại
`GET /api/v1/auth/me`
Response:
```
{
  "id": "user-uuid",
  "email": "customer@gmail.com",
  "fullName": "Nguyen Van A",
  "status": "ACTIVE",
  "roles": ["CUSTOMER"]
}
```
### API 4. Gán vai trò
`POST /api/v1/users/{id}/roles`
Request:
```
{
  "roleId": "role-uuid"
}
```
Response: `204 No Content`
Business Rules:
- User phải tồn tại.
- Role phải tồn tại.
- Không được gán trùng vai trò.
- Chỉ `ADMIN` được phép thực hiện.
- Nên bảo vệ role `ADMIN` cuối cùng không bị gỡ ngoài ý muốn.


```
{
  "id": "user-uuid",
```

`PATCH /api/v1/users/{id}/status`


- Không xóa vật lý người dùng đã có lịch sử đặt vé.
- Khi khóa tài khoản, cần có chính sách vô hiệu hóa phiên đăng nhập hiện tại.

## 8.3. Request và Response
### API 1. Tạo booking
`POST /api/v1/bookings`
Request:
```
{
  "flightScheduleId": "schedule-uuid",
  "passengers": [
    {
      "fullName": "Nguyen Van A",
      "dateOfBirth": "1998-05-20",
      "gender": "MALE",
      "documentNumber": "012345678",
      "flightSeatId": "flight-seat-uuid-1"
    },
    {
      "fullName": "Nguyen Van B",
      "dateOfBirth": "2000-08-15",
      "gender": "FEMALE",
      "documentNumber": "987654321",
      "flightSeatId": "flight-seat-uuid-2"
    }
  ]
}
```
Response `201 Created`:
```
{
  "id": "booking-uuid",
  "bookingCode": "BK202610130001",
  "flightScheduleId": "schedule-uuid",
  "status": "PENDING",
  "totalAmount": 3000000,
  "expiresAt": "2026-10-13T09:00:00",
  "passengers": [
    {
      "id": "passenger-uuid-1",
      "fullName": "Nguyen Van A",
      "seatNumber": "12A"
    },
    {
      "id": "passenger-uuid-2",
      "fullName": "Nguyen Van B",
      "seatNumber": "12B"
    }
  ]
}
```
Business Rules:
1. User phải đăng nhập và tài khoản `ACTIVE`.
2. `flightScheduleId` phải tồn tại và đang mở bán.
3. Danh sách hành khách không được rỗng.
4. Các `flightSeatId` trong request không được trùng nhau.
5. Tất cả ghế phải thuộc cùng `flightScheduleId`.
6. Tất cả ghế phải ở trạng thái thực sự có thể giữ.
7. `totalAmount` phải được tính tại backend từ giá ghế, không nhận từ client.
8. Một booking có thời hạn giữ ghế theo chính sách hệ thống, ví dụ 15 phút.
9. Tạo booking, passengers và chuyển trạng thái ghế phải nằm trong cùng một database transaction.
10. Nếu bất kỳ ghế nào không thể giữ, toàn bộ transaction phải rollback.
Ví dụ câu lệnh giữ ghế có điều kiện:
```
UPDATE flight_seats
SET status = 'HELD',
    held_by_booking_id = :bookingId,
    held_until = :expiresAt
WHERE id = :seatId
  AND flight_schedule_id = :scheduleId
  AND status = 'AVAILABLE';
```
Service phải kiểm tra số dòng được cập nhật. Nếu bằng `0`, ghế không còn khả dụng. Với nhiều ghế, phải kiểm tra kết quả của từng lần cập nhật và rollback toàn bộ nếu có bất kỳ thất bại nào.

### API 3. Hủy booking
`POST /api/v1/bookings/{id}/cancel`
Request: Không yêu cầu body trong phiên bản đầu.
Response:
```
{
  "id": "booking-uuid",
  "status": "CANCELLED"
}
```
Business Rules:
- Booking phải thuộc người dùng hoặc nhân viên có quyền.
- Với booking `PENDING`, nếu chưa thanh toán, hệ thống có thể hủy và giải phóng những ghế đang được giữ bởi booking đó.
- Chỉ giải phóng ghế khi `held_by_booking_id` đúng với booking hiện tại.
- Với booking `CONFIRMED`, không được tự động trả ghế về `AVAILABLE` nếu chưa có quy trình hủy vé và hoàn tiền.
- Không cho phép chuyển booking `EXPIRED` về `PENDING` bằng API này.
### API 4. Hết hạn booking
Không cần public API cho khách hàng để chuyển booking thành `EXPIRED`.
Hệ thống sử dụng Scheduled Job xử lý:
1. Tìm booking `PENDING` đã quá `expires_at`.
2. Xác nhận booking chưa có thanh toán thành công hoặc giao dịch đang cần đối soát.
3. Chuyển booking sang `EXPIRED`.
4. Giải phóng những ghế còn `HELD` bởi booking đó.
5. Thực hiện trong transaction.
6. Bảo đảm job có thể chạy lại an toàn.
Cần giải quyết tình huống thanh toán đang xử lý đúng thời điểm booking hết hạn. Không được chỉ dựa vào `expires_at` mà bỏ qua trạng thái thực tế của giao dịch thanh toán.

## 9.3. Request và Response
### API 1. Khởi tạo thanh toán
`POST /api/v1/bookings/{bookingId}/payments`
Request:
```
{
  "paymentMethod": "VNPAY"
}
```
Response `201 Created`:
```

  "paymentId": "payment-uuid",
  "bookingId": "booking-uuid",
  "amount": 1500000,
  "paymentMethod": "VNPAY",

}
```
`paymentUrl` ở đây chỉ là URL minh họa.
Business Rules:
- Booking phải thuộc user đăng nhập.
- Booking phải còn `PENDING` và còn hiệu lực thanh toán.
- `amount` lấy từ `bookings.total_amount`.
- Không nhận amount do client truyền lên.
- Backend tạo mã giao dịch/idempotency key riêng.
- Không mở database transaction trong suốt thời gian gọi API của nhà cung cấp.
### API 2. Nhận kết quả thanh toán
`POST /api/v1/payments/webhooks/vnpay`
Payload thực tế phụ thuộc vào nhà cung cấp, do đó không tự định nghĩa cố định JSON chung để thay thế payload của VNPAY.
Khi nhận thông báo thành công, hệ thống phải:
1. Xác thực chữ ký của provider.
2. Xác định payment tương ứng.
3. Kiểm tra `transaction_id` và số tiền.
4. Kiểm tra payment đã được xử lý hay chưa.
5. Kiểm tra booking và điều kiện xác nhận còn hợp lệ.
6. Chuyển payment sang `SUCCESS`.
7. Chuyển booking sang `CONFIRMED`.
8. Chuyển các ghế được giữ bởi booking sang `BOOKED`.
9. Commit transaction.
10. Tiến hành phát hành vé theo thiết kế module Ticket.
Nếu callback được gửi lặp lại, hệ thống không được xác nhận booking hoặc phát hành vé lần thứ hai.
Nếu provider báo thành công sau khi booking hết hạn và ghế đã được cấp cho người khác, phải chuyển giao dịch sang quy trình xử lý ngoại lệ/hoàn tiền hoặc đối soát. Không được tự động chiếm lại ghế của booking khác.
